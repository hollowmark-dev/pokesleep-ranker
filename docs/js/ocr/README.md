# ocr/ — スクショ読み取りのしくみ

ポケモンスリープの「ポケモン詳細」画面（縦長・1080〜1290px幅）を1枚読み込んで、
とくいタイプ・種族・レベル・SP・おてつだい時間・最大所持数・メインスキル・サブスキル5枠・
解放レベル・せいかく を取り出す。**読み取り結果はそのまま保存せず、必ず確認フォームを挟む**
（`views/view-capture.js`）。

## パイプライン

主経路は **layout.js（領域OCR）**。画面全体を1回で読む旧経路（parse.js）は、
アンカーが見つからなかったときのフォールバックとしてだけ残してある。

```
File
 └ image.js    fileToCanvas(color:true)  縮小（既定1080px幅・拡大は2倍まで）
 │                                       → 色つき canvas（アンカー検出用）
 │                                       → グレースケール＋コントラスト伸長 canvas（旧経路用）
 └ layout.js   findAnchors()             緑の見出し帯2本(H1/H2)・黄色い枠下辺(CB)を色で検出
 │             buildRegions()            アンカー相対の矩形13個（1080幅換算の表）
 │             image.prepareCrop()        切り出し→2倍→伸長→大津で二値化→必要なら反転
 │             engine.recognizePrepared() PSM.SINGLE_LINE で1枚ずつ読む
 │             → 各項目を fuzzy で照合して {value, conf}
 └ (アンカー欠損時のみ) engine.recognize() + parse.parseFields() で残りを埋める
 └ view-capture.js                       確認フォーム＋ライブ順位プレビュー → store へ保存
```

### なぜ領域ごとに読むのか

画面全体を1回で読むと、白抜きの見出しラベル・金色のチップ・茶色の小さなロックタグ・
せいかく名が軒並み落ちる（実測: s1 で期待18件中8件しか出ない）。
UIは画面幅に対して固定の比率で組まれているので、
**色でアンカーを3つ取り、そこからの相対座標で切り出して1行ずつ読む**方が確実に速く正確。

- **H1** … 「メインスキル・サブスキル」の緑帯の上端。`g>170 && r<120 && b<140 && g-r>80` を緑とみなし、
  x∈[60,860]（1080換算）のサンプルの60%以上が緑の行が20px以上続いたところ。
- **H2** … 2本目の緑帯（「詳細ステータス」）の上端。せいかく欄の基準。
- **CB** … メインスキル枠の**下**辺（太い黄色線）。`r>225 && 150<g<215 && b<110`、
  x∈[300,800] の70%以上が黄色の行。枠の高さは説明文の行数（1〜4行）で変わるので、
  サブスキルのチップ5枚はここを基準にする。枠の**上**辺はこの黄色判定に掛からないため、
  H1より下の最初の黄色ランがそのまま下辺になる。

チップは `top = CB + (82 + 170*r)` の3行2列（行優先）。文字は枠の内側だけを切る
（上端にはロックタグが11pxほど被るので `top+14 .. top+88`）。

### ロックタグ・とくいタイプ・▲▼ は読まない

- **解放レベル**はゲームのルールで枠ごとに固定（`SUBSKILL_UNLOCK_LEVELS` = 10/25/50/70/80）。
  小さな茶色タグをOCRする価値はないので、読まずに定数を入れる（conf=1）。
- **とくいタイプ**は画面左上の「きのみ」ピルではなく `SPECIES[...].specialty` から引く
  （あのピルはきのみ欄のラベル）。種族が特定できなければ null。
- **せいかくの▲▼効果**はせいかく名から一意に決まるので読まない。

### 全体一致を部分一致より優先する（pickBest）

切り出した領域には項目が1つしか写っていないので、`fuzzy.bestMatch` の
「部分一致でも満点」は都合が悪い。`いやしのはどう(げんきエールS)` が
`げんきエールS`（部分一致・比率1.0）に吸われてしまう。
`layout.pickBest()` は部分一致に `subPenalty`（既定0.9）を掛け、全体一致を勝たせる。

### なぜ行を組み直すのか（rebuildLines / 旧経路）

tesseract の日本語は 1〜3文字ごとに「単語」が切れるため、`words` をそのまま使うと
「おてつ」「だい」「時間」のようにバラバラになる。そこで

- **y方向の範囲が重なる** トークンを同じ段にまとめ、
- その中で **x方向の隙間が文字高の1.5倍以上** 空いたら別カラムとして切り離す

という2段階で行を復元している。x方向で切るのが重要で、これがないと
画面上部の「SP 402」と右側のきのみアイコンの「Lv. 30」タグが1行に混ざり、
レベルの読み取りが壊れる。

### 見出し語アンカー方式（parse.js・フォールバック）

緑帯が見つからない画像（画面の一部だけのスクショなど）でだけ使う。
固定座標は一切使わない。画面の見出し語を探して、その周辺だけを読む。

| 項目 | アンカー | 取り出し方 |
|---|---|---|
| SP | `SP` | `SP` に続く数字 |
| レベル・種族 | SPの行に近い `Lv.NN` の行 | 種族名の一致度・SP行との距離・x位置の合成スコアで1行選ぶ |
| とくいタイプ | 種族行より上の行 | 4語とのあいまい一致。**種族テーブルの `specialty` と食い違ったらテーブルを優先し確度を下げる** |
| おてつだい時間 | 「おてつだい時間」 | `N時間M分S秒` → 秒。時間の表記がある個体もあるので必ず3要素で見る |
| 最大所持数 | 「最大所持数」 | `N個`。サブスキル「最大所持数アップM」と紛れるので、`個` が取れた最初の行だけ採る |
| メインスキル | 最大所持数の行〜「詳細ステータス」 | `MAIN_SKILLS` との最良一致。`Lv.N` は同じ段の別カラムにあるので行の"ピア"も見る |
| サブスキル5枠 | メインスキル行〜「詳細ステータス」 | `SUBSKILLS` と0.75以上で一致した行を、bboxで 行→列 の順に並べ直して枠1..5 |
| 解放レベル | チップの上に乗る `🔒 Lv.NN` タグ | **同じ列で「すぐ下」のチップ**に割り当てる。順番に詰めない（Lv60個体では枠4,5だけロックされる） |
| せいかく | 「せいかく」 | ラベルの真下の行を `NATURES` と照合。さらに ▲▼ の効果テキストで裏取り |

**値はラベルの真下ではなく右隣にあり、しかも数px上にあることが多い。**
y でソートすると値の行がラベルより先に来るので、`searchTexts()` は
「ラベル行の残り → 同じ段の別カラム → 前後の行」の順に探索範囲を広げている。

### S / M / L の一文字問題

`おてつだいスピードS` と `おてつだいスピードM` は編集距離1しか違わず、名前一致だけでは決まらない。
そこで **名前の基底部分（末尾のS/M/Lを取ったもの）で一致させてから、
マッチした部分文字列の末尾の英数字1文字でサイズを決め直す**（`fuzzy.sizeLetter`、
`S`/`5`→S、`M`→M、`L`/`1`/`I`→L）。判定できなければ確度を 0.75倍して「要確認」に落とす。

## 調整つまみ

主経路は `layout.js` の `LAYOUT_TUNING`。

| キー | 既定 | 効き方 |
|---|---|---|
| `speciesThreshold` | 0.62 | 領域が1項目だけなので旧経路より緩めてよい |
| `mainSkillThreshold` | 0.6 | 括弧つきの固有名（`いやしのはどう(げんきエールS)`）を取り逃さない値 |
| `subskillThreshold` | 0.6 | チップ1枚だけを読むので説明文が混ざる心配がない。旧経路の0.75より緩い |
| `natureThreshold` | 0.62 | せいかく名は3〜5文字 |
| `subPenalty` | 0.9 | 部分一致への減点。下げすぎると長い正式名が取れず、1.0にすると括弧つきが短い名前に吸われる |
| `cropScale` | 2 | 切り出しの拡大率。1にすると小さい文字が落ちる |
| `greenBarMinRatio` / `greenBarMinHeight` | 0.6 / 20 | 緑帯の検出。「きのみ」ピルなど幅の狭い緑は40%程度なので0.6で切れる |
| `yellowMinRatio` / `yellowMinHeight` | 0.7 / 3 | 枠の黄色い下辺の検出。左右とも金色のチップが並ぶ行を拾わない値 |

矩形そのものは `buildRegions()` の表（1080幅換算）にまとめてある。UIが変わったらここだけ直す。

フォールバック（`parse.js`）の `TUNING`:

| キー | 既定 | 効き方 |
|---|---|---|
| `speciesThreshold` | 0.7 | 下げると未登録種族を誤って既知の種族に寄せる。上げると `species:null`（`rawName` だけ）が増える |
| `specialtyThreshold` | 0.7 | 「きのみ」「オール」は3文字しかなく、下げすぎると誤検出しやすい |
| `mainSkillThreshold` | 0.62 | スキル名は長いので緩めでよい。上げすぎると `いやしのはどう(げんきエールS)` のような括弧つきを取り逃す |
| `subskillThreshold` | 0.75 | **いちばん重要**。下げるとメインスキルの説明文（「げんきを6回復し、」など）を拾い始める。実測では説明文の最良一致が0.60前後なので0.75は十分な余裕がある |
| `natureThreshold` | 0.67 | せいかく名は3〜5文字。下げると効果テキストを誤って拾う |
| `chipMaxLen` | 24 | チップ候補として許す正規化後の文字数。説明文を落とすための長さガード |
| `rowGapFactor` | 0.6 | チップの行分割。行高の中央値×この値より縦にずれたら次の行と見なす |

`engine.js` 側のつまみ:

- **PSM** — 全体は `PSM.SPARSE_TEXT`（11）。この画面は文字が散らばっているので
  `AUTO`(3) や `SINGLE_BLOCK`(6) より確実に良い。個別の行を読み直すときだけ
  `recognizeRect(canvas, rect, PSM.SINGLE_LINE)` を使う。
- **targetWidth**（`image.js`）— 既定1080。上げても精度はほぼ変わらず時間だけ延びる。
  小さいスクショは2倍までしか拡大しない。

## デバッグのしかた

1. 確認フォームの折りたたみ **「OCR生テキスト」** を開く。前処理後のサムネイル、
   検出したアンカー（H1/H2/CB/倍率）、`[項目] 読めた文字` の一覧が出る。
   - アンカーが `—` なら色判定（`findAnchors`）の問題。スクショが加工されている可能性。
   - アンカーは出ているのに特定の項目だけ空 → その矩形がずれている（`buildRegions`）。
   - 文字は出ているのにフォームが空 → しきい値（`LAYOUT_TUNING`）かマスタデータ側の問題。
2. `parseScreenshot()` の戻り値の `debug`:
   - `debug.anchors` … `{ H1, H2, CB, scale }`
   - `debug.regions` … `[{ field, rect, rawText }]`。`rect` をそのまま `image.prepareCrop()` に
     渡せば、その領域の二値化結果を目で確認できる。
3. 旧経路（`parseFields()`）の `debug`:
   - `debug.lines` … 復元後の全行とその bbox
   - `debug.anchors.speciesLine` / `mainSkillLine` … どの行をアンカーに選んだか
   - `debug.anchors.unlockTags` … `Lv.NN` タグをどの枠に割り当てたか
4. 枠の並び順がおかしいときは `debug.lines` の bbox を見て、
   チップが2列に分かれて取れているか（x が2グループになっているか）を確認する。
   1列に潰れているなら `rebuildLines` の x ギャップ判定（文字高の1.5倍）を疑う。
5. 色背景に淡色の文字（ロック中のチップ）が読めないときは、
   `image.invertCanvas()` + `engine.recognizeRect()` でその矩形だけ読み直せる。
   主経路の `prepareCrop()` は「黒が過半なら反転」を自動でやるので通常は不要。

## fast と best の traineddata について

`vendor/lang/jpn.traineddata.gz` は **tessdata_fast** を同梱している。

- **fast**（既定・約6MB圧縮）… 初回ダウンロードが軽く、認識も1〜3秒で終わる。
  この画面はフォントが1種類・高コントラストなので fast で十分読める。
- **best**（約20MB以上）… 精度は上がるがモデルの読み込みだけで体感が悪化する。
  スマホのモバイル回線で初回6MBでも「重い」寄りなので、**best には替えない**方針。

初回だけ traineddata を取りに行くため、`view-capture.js` は1回目の読み取りで
「初回はOCRデータ約6MBを読み込みます」と表示する。2回目以降は
`cachePath: 'psr'` の IndexedDB キャッシュから読むので速い。
`gzip: true` と `langPath` の明示は必須（省略すると既定のCDNへ取りに行ってしまう）。
