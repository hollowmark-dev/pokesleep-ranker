## 0. 先に結論

1. **`ingredients.js` の17食材は古い。現在は19食材。** 2025-10-22頃に「つやつやアボカド」（アンバー渓谷実装）、2026-04下旬に「ずっしりカボチャ」（バケッチャ系統関連実装）が追加されている。この2つを `INGREDIENTS` に追加する必要がある（詳細は1章）。
2. **エナジー値そのものは仮データと実データでほぼ一致**（tomato:110, leek:185 など）。ずれているのは新規2種の欠落のみで、既存17食材の数値は複数ソースで裏取りできた。
3. **食材の「汎用価値」は、エナジーだけで決めると誤る。** コミュニティの一次情報は「①基礎エナジー」「②高評価レシピでの採用頻度」「③入手できるポケモンの少なさ（ボトルネック性）」の3軸で語られており、単純にエナジーが高い＝価値が高いわけではない（例: おいしいシッポ/ずっしりカボチャ/つやつやアボカドはエナジー最上位だが採用レシピが2〜3種と少なく、汎用性では中位にとどまる）。
4. **食材構成（AAA/AAB/ABB/ABC）の評価は、コミュニティ内で割れている。** 「単一食材を持つ得意ポケモンの厳選」という文脈では **AAA/ABB が定番**（狙った食材が確実に手に入る）という意見が主流。一方で「ABC肯定論」のように、**ABCはむしろ貯蔵する食材の種類が増えて汎用的**という逆の主張も存在する。この対立は「単一レシピを効率よく回す用途」と「幅広いレシピに対応する用途」のどちらを見ているかの違いであり、後者は本アプリの方針（汎用寄り）と一致する。
5. **本アプリの方針（揃いボーナスは控えめ・汎用寄り）は、コミュニティの主流（AAA推し）とは逆方向。** これは矛盾ではなく、**「単一得意ポケモンの厳選基準」と「幅広いレシピをこなすプレイヤーの評価軸」が違う問題を解いている**ため。3章・4章で具体案を出す。

## 2. 汎用価値（general-purpose value）の評価軸

コミュニティが「食材の価値」を語るときの根拠は、単一のランキング記事というより **3つの軸の合成** としてバラバラに語られている。それぞれの一次情報は次の通り。

### 2-1. ①基礎エナジー

そのまま採用されることが多いが、**「エナジーが高い食材をたくさん持ってこられるとゲームバランスが崩れるので、逆に高エナジー食材ほど入手性を絞ってある」**という設計原則がコミュニティで共有されている。

> 「食材エナジーが高いものをたくさん持ってきたらそれこそゲームバランスが崩れてしまう」（note「食材タイプのポケモン比較・食材指数の話」／えみさり）

つまりエナジーが高い食材は、放っておいても入手数の少なさで価値が相殺される設計になっている。単純にエナジー値をそのまま `ingredientValues` にするのは避けるべき。

### 2-2. ②高評価レシピでの採用頻度（カレー/サラダ/デザート）

ポケらく「料理とレシピ(食材)一覧」の集計によると、高得点帯のレシピで頻出する食材と、逆にほぼ使われない食材がはっきり分かれる。

| 頻度帯 | 食材 | 備考 |
|---|---|---|
| 最頻出（12種以上のレシピ） | あまいミツ | デザート・カレー双方で共通食材 |
| 高頻出（10種前後） | モーモーミルク | デザート全般の軸 |
| 高頻出（8種前後） | ピュアなオイル、ワカクサコーン | サラダ／カレー双方で頻出 |
| 中頻出（6〜7種） | マメミート、とくせんエッグ、ワカクサ大豆 | |
| カテゴリ定番 | あったかジンジャー、げきからハーブ（カレー）／あんみんトマト（サラダ） | ジャンル特化だが、そのジャンル内では必須級 |
| **低頻出（2〜3種）** | **おいしいシッポ、つやつやアボカド、ずっしりカボチャ** | **エナジーは最上位だが、対応レシピが少ない＝汎用性は低い** |

> 「頻出食材を優先的に収集することで、複数の高得点レシピ作成に対応できる効率性が向上します」（ポケらく「料理とレシピ(食材)一覧」の分析より）

これは本アプリの前提（「1レシピ特化ではなく、色々なレシピを作るプレイヤー」）に直結する軸であり、**エナジーが高くても採用レシピ数が少ない食材は汎用価値で割り引くべき**という根拠になる。

### 2-3. ③入手のしづらさ（ボトルネック性）

「食材が足りない時の対処法」系記事（Game8）には個別食材のボトルネック指定は薄いが、**ポケらくの獲得数量ランキング（食材別）** や個別記事の記述から、下記の食材が「持っている・大量に持ってくるポケモンが少ない」＝ボトルネックとして繰り返し言及される。

- **ふといながねぎ（leek）**: 「基礎エナジーが高い食材の中でも入手できるポケモンが限定的。主にLv.60の限定ポケモン数体のみ」（ポケらく）。※印付きレア食材（wikiwiki）。
- **おいしいシッポ（tail）**: 「最もレアな食材」（複数ソース）。Lv1で拾えるポケモンが存在しない。
- **ワカクサ大豆・ワカクサコーン・めざましコーヒー・リラックスカカオ**: 上位を持つポケモンが限られる（ゴローニャ／ウソハチ／エスカタン等特定種のみ高数量、というポケらくのランキング傾向）。ユーザー想定と一致。

これらは「持っている人が少ない＝手に入れたときの限界価値が高い」という意味でのボトルネックであり、必ずしも「使えるレシピが多い」わけではない点に注意（②と③は別軸で、時に逆方向に働く）。

## 3. 食材構成（AAA/AAB/ABB/ABC）のコミュニティ評価と、本アプリでの扱い

### 3-1. 用語の確認

Lv1〜の確定枠食材をA、Lv30〜の追加パターン食材をB、Lv60〜の追加パターン食材をCと呼ぶ（Game8）。AAA＝3枠とも同一食材、AAB/AAC＝2枠が同一＋1枠別、ABC＝3枠とも別食材。

### 3-2. 「単一得意ポケモンの厳選」文脈での主流意見（＝AAA/ABB推し）

- 「食材構成は『AAA（第1食材統一）』または『ABB』がおすすめ」「AAA構成は迷わず育成推奨。欲しい食材がすぐ手に入るという圧倒的なメリット」（課金中毒者の日記「食材の組み合わせごとの評価」）
- 「AAB＆AACは汎用性が高く、AAAが引けなかった場合や育成済みの場合は育成することが推奨」（同上）
- 「ABCはピンポイントで作りたいレシピが無ければ無理して育成しなくてOK」（同上）
- おがのブログの厳選基準では「AAA（第1食材統一）またはABBがおすすめ」「必要な食材は調理環境次第で変わるため、ABCの多様性はむしろ環境変化に弱くなりうる」という論旨。

ここでいう「汎用性」は**「このポケモン1匹で、狙った食材を安定して集められるか」**という意味であり、本アプリが定義する「幅広いレシピをこなすプレイヤーにとっての価値」とは論点が異なる点に注意。

### 3-3. 少数だが実在する「ABC肯定論」（＝本アプリの方針に近い）

カイリューを例にしたnote記事は、ABC構成を次の理由で積極評価している。

> 「食材とくいAAAよりもABCのほうが様々な食材を貯められます」（note「ABC肯定論_カイリューの食材構成」）

論拠は3つ：①ABCでも需要の高い食材（オイル等）の集約量で上位AA個体に対抗できる場合がある、②ハーブ・コーンのような「あれば助かる」汎用食材を複数枠で拾える、③ポケモン自体の基礎性能が高ければABCでも見劣りしない。

これは「1匹で複数種の食材を平行して備蓄できる＝レシピの引き出しが増える」という発想であり、**本アプリの「汎用寄り」の思想（多くのレシピで使える食材を高く評価し、揃いボーナスは控えめにする）と方向性が一致する少数派意見**。

### 3-4. 本アプリでの推奨: 揃いボーナスは小さく、ABC側に軽い多様性ボーナスを足す

コミュニティの主流（AAA推し）は「単一得意ポケモンをどう厳選するか」という別の問題を解いており、そのままでは採用しない。SPEC.mdの前提（食材構成は「サブスキル1〜1.5枠分」の重み、揃いボーナス控えめ）に対して、以下を提案する。

- **`same3`（AAA）ボーナスは小さく**: 「同じ食材を3枠持つ」ことで得られる実利は「特定食材の収集効率」であり、幅広いレシピを作るプレイヤーには過大評価しない。目安として、最高価値食材1個ぶん（10点）の**半分〜7割程度**（後述4章で `same3: 6` を提案）。
- **`same2`（AAB/ABB）ボーナスはさらに小さく**: 主流意見でも「AAAが引けなかった場合の代替」という位置づけであり、汎用性の観点では独立した価値はほぼない。`same2: 2` 程度を提案。
- **ABC（全部バラバラ）には現状の schema にボーナス項目が無いが、3-3の少数派意見（多様な食材を並行して備蓄できる）を汲んで、独立した小さな多様性ボーナスの追加を検討する価値がある。** 具体的には `ingredientUniformityBonus` に `allDifferent`（仮称、例: 3点）を追加し、3枠がすべて異なる食材のときに加点する。ただし優先度は低く、まずは `same3`/`same2` を小さくするだけでも「汎用寄り」の方針は十分に反映できる。

## 4. `ingredientValues` / `ingredientUniformityBonus` / `ingredientWeights` の具体案

### 4-1. `ingredientValues`（0..100、最高値=100）

**方法**: `raw = energy × 採用レシピ頻度係数 × ボトルネック係数` を計算し、最大値（おいしいシッポ）を100として正規化。頻度係数は2章②のバケット（低頻度2〜3種=0.5／中頻度6〜7種=0.8〜0.85／カテゴリ定番=0.9／最頻出=1.0）、ボトルネック係数は2章③の言及有無（言及なし=1.0、moderate=1.05、明示的ボトルネック=1.15、最レア=1.2）を採用した。**この式自体は本レポートの提案であり、コミュニティに既製の「汎用スコア表」は存在しない**（各ソースはエナジー表か採用頻度かボトルネックのどれか一つしか出していない）ため、3軸を統合する設計判断として提示する。

### 4-2. `ingredientUniformityBonus`

```js
ingredientUniformityBonus: {
  same3: 6,  // AAA。汎用価値の観点では過大評価しない（最高食材1個=10点の6割程度）
  same2: 2,  // AAB/ABB。厳選コミュニティでは「AAA未達の代替」止まりで独立価値は薄い
  // 将来拡張案（現行スキーマ外）: allDifferent: 3  // ABC。少数派の「多様な食材を並行備蓄できる」論を汲む
}
```

理由: SPEC.mdの前掲例（`same3: 10, same2: 4`）はやや厚めで、コミュニティの主流評価（AAA推し）に引っ張られやすい。本アプリの方針（汎用寄り・揃いボーナス控えめ）に沿うなら、`same3` は「最高食材1個ぶん」を上回らない範囲（6割程度）に抑え、`same2` はほぼ無視できる水準（2割程度）にとどめるのが妥当。

### 4-3. `ingredientWeights`（specialty別）

```js
ingredientWeights: { berry: 10, ingredient: 100, skill: 20, all: 40 }
```

- `ingredient: 100`（基準）: 食材得意ポケモンの評価は食材構成が主役。Game8「AAA個体が基本的におすすめ」の対象そのもの。
- `berry: 10`: 「きのみ得意ポケモンは食材枠は全く気にしなくてOK」（おがのブログ、Game8系の厳選記事で共通）。ゼロにせず10とするのは、きのみ得意でも食材おてつだいが発生し得るため微小な影響は残す趣旨。
- `skill: 20`: 「スキル得意ポケモンは拾う数が少ない食材を優先。AAA構成は重視不要」（同上）。**構成（揃い）は不要だが食材の価値自体はゼロではない**ため、ingredient(100)よりかなり低いが berry よりは高めに設定。
- `all: 40`: SPEC.mdの既存例を踏襲。オール型はきのみ・食材・スキルいずれも中庸に評価すべきという設計思想（R3調査の「器用貧乏にさせず、きのみ・食材・スキルのどれかに尖らせる」という記述とも整合）に対し、食材構成の重みも中間的な水準とする。
